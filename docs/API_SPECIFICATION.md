# API Specification

**Status:** Normative design for MVP; endpoint details may be versioned before implementation.  
**Base path:** `/api/v1`  
**Transport:** HTTPS JSON; Server-Sent Events (SSE) for chat streaming.

## 1. API principles

- All tenant-owned resources are scoped to a workspace and authorized server-side.
- The authenticated application backend is the authority for end-user identity and permissions. A browser-supplied user ID is never proof of identity.
- Use opaque UUID/ULID identifiers; never expose database sequence values.
- Use ISO-8601 UTC timestamps, JSON request/response bodies, and UTF-8.
- Mutating operations require idempotency where retries could duplicate effects.
- Unknown fields are rejected for security-sensitive configuration and accepted only where explicitly documented for forward compatibility.
- All endpoints require TLS. CORS is allow-list based and is not an authorization mechanism.

## 2. Authentication classes

| Caller | Credential | Scope |
|---|---|---|
| Dashboard user | SaaS session/OIDC token | Membership and role checks |
| Workspace server | Workspace API key or OAuth client credential | Explicit workspace scopes |
| Embedded widget | Short-lived signed widget session token | One workspace, agent, origin and session |
| Customer end user | Signed identity assertion exchanged server-to-server | One workspace and external subject |
| Platform operator | Admin session + MFA | Explicit platform-admin permissions |

Secrets are sent in authorization headers, never query strings. Store only hashes of platform-issued API tokens; show a secret once at creation. Customer provider keys and connector credentials are encrypted using envelope encryption and are never returned by read APIs.

## 3. Common conventions

### Headers

- `Authorization: Bearer <token>`
- `Content-Type: application/json`
- `Idempotency-Key: <opaque-value>` for eligible writes
- `X-Request-Id` is generated by the server; clients may send a bounded correlation ID.
- `Last-Event-ID` may be used to resume an SSE stream where replay is supported.

### Success envelope

```json
{
  "data": {},
  "meta": { "request_id": "req_...", "api_version": "v1" }
}
```

Collection responses additionally include `page`: `{ "limit": 50, "next_cursor": "..." }`. Cursor pagination is stable, opaque and tenant-scoped.

### Error envelope

```json
{
  "error": {
    "code": "validation_error",
    "message": "The request is invalid.",
    "details": [{ "field": "name", "reason": "required" }],
    "retryable": false
  },
  "meta": { "request_id": "req_...", "api_version": "v1" }
}
```

Do not return stack traces, SQL, provider secrets, internal hostnames or raw upstream error bodies.

### HTTP status policy

| Status | Meaning |
|---|---|
| 200 | Successful read or completed operation |
| 201 | Resource created |
| 202 | Accepted asynchronous operation |
| 204 | Successful operation with no body |
| 400 | Malformed request |
| 401 | Missing/invalid authentication |
| 403 | Authenticated but not authorized |
| 404 | Missing or intentionally concealed resource |
| 409 | State conflict or idempotency conflict |
| 422 | Semantically invalid input |
| 429 | Rate or quota limit |
| 502 | Upstream dependency failure |
| 503 | Temporarily unavailable |
| 504 | Upstream timeout |

## 5. Chat request contract

```json
{
  "content": "How do I update my subscription?",
  "client_message_id": "client-generated-opaque-id",
  "attachments": [],
  "stream": true,
  "metadata": {}
}
```

The server derives workspace, agent, identity, roles, locale and policy from the verified session. Client metadata is untrusted, size-limited and must not override authorization or system instructions. Attachments refer to previously uploaded, access-controlled objects; raw arbitrary URLs are not accepted as attachments.

A successful non-streaming response returns an assistant message, usage summary safe for the caller, and citations/tool activity allowed by policy. Streaming uses SSE events:

- `message.started`
- `message.delta` with text fragment
- `tool.started` and `tool.completed` with redacted display metadata
- `citation`
- `message.completed` with final message and usage
- `message.failed` with stable error code
- `message.cancelled`

Events include `event_id`, `session_id`, `message_id`, and timestamp. Never stream chain-of-thought, hidden prompts, raw tool arguments containing secrets, or internal policy text.

## 6. Identity exchange

Workspace backend signs a short-lived assertion containing issuer, audience, subject, issued-at, expiry, nonce, and optional verified profile/claims. The SaaS validates signature against a registered key, exact issuer/audience, clock skew, expiry, nonce replay, and workspace binding. It returns a short-lived, scoped session token. Identity claims are minimized and mapped to explicit attributes; customer authorization remains authoritative and must be rechecked for sensitive actions.

## 7. Rate limits and quotas

Apply layered limits by IP, workspace, session, actor, endpoint and provider. Return 429 with `Retry-After` and a stable error code. Chat token budgets and provider spend limits are distinct from HTTP request limits. Limits must be configurable, observable and fail closed for abuse-sensitive actions.

## 8. Webhooks

Outbound webhooks are an optional post-MVP capability. When enabled: sign payloads with per-endpoint rotating secrets; include timestamp and unique event ID; retry with bounded exponential backoff; provide delivery logs and replay; require HTTPS; block private, loopback, link-local and metadata destinations; and never include secrets or unnecessary personal data. Consumers must deduplicate by event ID.

## 9. Versioning and compatibility

- Additive optional response fields are backward-compatible.
- Breaking changes require a new major API path and migration window.
- Deprecations include a date, replacement and migration guide.
- Widget protocol and server API versions are negotiated independently.
- OpenAPI 3.1 schemas must be generated from the same source as runtime validation, then committed under `docs/openapi/` when implementation begins.

## 10. Acceptance criteria

- Every route has an explicit caller class, scope, authorization rule and tenant boundary.
- Every write has validation, audit behavior and idempotency decision.
- Cross-workspace IDs return a non-disclosing 404 or equivalent.
- SSE terminal events are mutually exclusive and every accepted message reaches a terminal state.
- Contract tests cover success, invalid input, unauthorized, forbidden, cross-tenant, rate-limited and upstream failure paths.
- No endpoint returns credential material after creation.
